# Permissions

Planning never authorizes implementation work. The durable execution agent uses the worker profile's workspace-write policy because the same provider conversation must perform accepted repairs and reconciliation. Verification phases explicitly prohibit edits; BDFL does not send a repair continuation until the user accepts a remedy.

Workers default to BDFL's accept-edits policy inside their isolated worktree. The durable profile records this as `workspace-write`; provider adapters translate it to Claude's `acceptEdits` mode or the Codex workspace-write sandbox. Ollama sessions use that same Codex sandbox after the Ollama launch separator. BDFL never defaults any role to Claude `bypassPermissions` or the Codex `danger-full-access` sandbox.

Direct sessions also use the durable `workspace-write` profile, but they run in the selected repository rather than a managed worktree. A direct agent is standalone: BDFL does not issue it a capability descriptor, expose the BDFL MCP server, install a Claude plugin or `bdfl-plan` skill, add planning or worker role instructions, or attach it to managed execution state. Its provider-native attention hooks and exact provider-session identity remain enabled so it can be closed and resumed normally.

Planning and direct presets are stored independently in the repository's schema-2 configuration. Updating the editable direct-agent profile does not change the planning delegator, worker, or capacity preset, and updating a planning preset does not change the direct profile. Repositories created before direct sessions continue to load as planning sessions.

Agent options can explicitly select safe alternatives to these defaults. Claude `--permission-mode` values other than `bypassPermissions` pass through unchanged. Codex `--sandbox`, `--ask-for-approval`, and their configuration equivalents also pass through when they do not select `danger-full-access`; Ollama forwards those options to its underlying Codex session. When an option supplies a safe sandbox or permission mode, BDFL does not append a conflicting role default.

Dangerous provider options cannot be stored in an agent profile. `bdfl --dangerous` is the only bypass opt-in: it launches Claude with `--dangerously-skip-permissions` and launches Codex or Ollama-backed Codex with `--dangerously-bypass-approvals-and-sandbox`. The switch applies to every agent launched or restored during that supervisor process and is not persisted.

Permission is only one boundary. BDFL also verifies actual changed paths against the approved chunk or full approved path union, reruns deterministic argv-based checks, and keeps conflicts inside generated worktrees. Every check is an argv array, runs without a shell, and has a hard deadline; integration checks run in background processes so they cannot freeze the supervisor. Final integration refuses a changed target branch, uncommitted target changes, or rewritten history. Clean descendant commits are preserved through a durable per-repository queue. If Git cannot combine the active item automatically, BDFL continues the same visible execution agent in the disposable reconciliation worktree, reruns global checks, and gives that agent a final read-only verification phase before advancing the target. Later queue items cannot reconcile against the same target concurrently.

Custom profile commands never pass through a shell. BDFL owns provider/profile selection, resume, MCP, model, effort, hook/settings, notification, dangerous access, and role flags; safe provider-native permission, sandbox, and approval options remain user-controlled.
